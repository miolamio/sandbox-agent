## Create a client

```ts
import { SandboxAgent } from "sandbox-agent";

const sdk = await SandboxAgent.connect({
  baseUrl: "http://127.0.0.1:2468",
});
```

`SandboxAgent.connect(...)` now waits for `/v1/health` by default before other SDK requests proceed. To disable that gate, pass `waitForHealth: false`. To keep the default gate but fail after a bounded wait, pass `waitForHealth: { timeoutMs: 120_000 }`. To cancel the startup wait early, pass `signal: abortController.signal`.

With a custom fetch handler (for example, proxying requests inside Workers):

```ts
const sdk = await SandboxAgent.connect({
  fetch: (input, init) => customFetch(input, init),
});
```

With an abort signal for the startup health gate:

```ts
const controller = new AbortController();

const sdk = await SandboxAgent.connect({
  baseUrl: "http://127.0.0.1:2468",
  signal: controller.signal,
});

controller.abort();
```

With persistence (see [Persisting Sessions](/session-persistence) for driver options):

```ts
import { SandboxAgent, InMemorySessionPersistDriver } from "sandbox-agent";

const persist = new InMemorySessionPersistDriver();

const sdk = await SandboxAgent.connect({
  baseUrl: "http://127.0.0.1:2468",
  persist,
});
```

Local spawn with a sandbox provider:

```ts
import { SandboxAgent } from "sandbox-agent";
import { local } from "sandbox-agent/local";

const sdk = await SandboxAgent.start({
  sandbox: local(),
});

// sdk.sandboxId — prefixed provider ID (e.g. "local/127.0.0.1:2468")

await sdk.destroySandbox(); // provider-defined cleanup + disposes client
```

### Agent authentication

When the SDK first connects to an agent, the agent may list the sign-in methods it supports. By default the SDK picks an API key method it recognizes (`codex-api-key`, `openai-api-key`, or `anthropic-api-key`) and ignores any failure, because the agent may already have credentials from environment variables or credential files.

Pass `auth` to `SandboxAgent.connect(...)` or `SandboxAgent.start(...)` to choose the method yourself:

```ts
// Always use one method id.
const sdk = await SandboxAgent.connect({
  baseUrl: "http://127.0.0.1:2468",
  auth: { methodId: "gateway-token" },
});

// Or pick per agent from the methods the agent lists.
const sdk2 = await SandboxAgent.connect({
  baseUrl: "http://127.0.0.1:2468",
  auth: {
    selectMethod: (methods, { agent }) => {
      if (agent !== "codex") return undefined; // use the default selection
      return methods.find((method) => method.id.includes("api-key"))?.id;
    },
  },
});
```

- `methodId`: used for every agent. Takes precedence over `selectMethod`.
- `selectMethod(methods, { agent })`: receives the full `AuthMethod[]` list (including `description` and `_meta`). Return a method id to use it, `false` to skip sign-in for that agent, or `undefined` to fall back to the default selection.
- `auth: false`: never sign in automatically.

A method chosen through `methodId` or `selectMethod` must be one the agent lists, otherwise `createSession(...)` rejects. If the agent refuses the chosen method, `createSession(...)` rejects with an error naming the agent and the method instead of continuing unauthenticated. Agents that list no sign-in methods are used as is, whatever `auth` says.

`SandboxAgent.start(...)` requires a `sandbox` provider. Built-in providers:

| Import | Provider |
|--------|----------|
| `sandbox-agent/local` | Local subprocess |
| `sandbox-agent/docker` | Docker container |
| `sandbox-agent/e2b` | E2B sandbox |
| `sandbox-agent/daytona` | Daytona workspace |
| `sandbox-agent/agentcomputer` | Agent Computer managed worker |
| `sandbox-agent/vercel` | Vercel Sandbox |
| `sandbox-agent/cloudflare` | Cloudflare Sandbox |

Use `sdk.dispose()` to disconnect without changing sandbox state, `sdk.pauseSandbox()` for graceful suspension when supported, or `sdk.killSandbox()` for permanent deletion.

## Session flow

```ts
const session = await sdk.createSession({
  agent: "mock",
  cwd: "/",
});

const prompt = await session.prompt([
  { type: "text", text: "Summarize this repository." },
]);

console.log(prompt.stopReason);
```

`session.prompt(...)` resolves when the whole turn ends, which can take as long as the server's agent request timeout (2 hours by default, see `--acp-request-timeout-ms` in the [CLI reference](/cli)). The SDK receives the result over the session's event stream, so a long turn is not cut off by HTTP client timeouts such as the 300 second response-header timeout of Node.js `fetch`. If the event stream is still connecting or reconnecting, the prompt waits up to 10 seconds for it. If the stream cannot connect (for example, the server is unreachable), the prompt is sent as a plain request whose result comes in the HTTP response, and HTTP client timeouts apply again.

The server keeps the most recent 1024 events of each agent server for clients that reconnect. A client that falls behind while connected catches up from these buffered events. If more events were produced while a client was disconnected, the older ones are gone: the server then tells the client which events were lost and sends the events it still has. A pending `session.prompt(...)` whose result is among those events resolves normally. If its result is not among them, it fails with an error saying the events were lost, instead of waiting forever. The turn itself may still be running on the server.

Load and destroy:

```ts
const restored = await sdk.resumeSession(session.id);
await restored.prompt([{ type: "text", text: "Continue from previous context." }]);

await sdk.destroySession(restored.id);
```

`resumeSession` first tries to reattach to the agent server the session last ran on (`session.serverId`). If that server is still running and the agent supports resuming sessions, the same agent session continues without replaying history. Otherwise the SDK creates a new agent session and replays recent history on the next prompt. In both cases the previously selected mode and config options (model, thought level, and others) are applied again.

If some of those settings can no longer be applied, `resumeSession` throws `SessionConfigRestoreError`. The session is still restored: use `error.session` to continue and `error.failures` to see which values were not applied.

```ts
import { SessionConfigRestoreError } from "sandbox-agent";

let restored;
try {
  restored = await sdk.resumeSession(session.id);
} catch (error) {
  if (!(error instanceof SessionConfigRestoreError)) throw error;
  console.warn(error.failures);
  restored = error.session;
}
```

### Several clients on one session

A second `SandboxAgent` (for example an orchestrator or a UI that watches) can call `resumeSession(id)` on a session another client created, sharing the same persistence driver. It attaches to the agent server that is already running, receives the session's events, and can send prompts too. The roles are:

- **Server ownership.** The client that started an agent server owns it. `sdk.dispose()` deletes only the servers that client started; a client that attached to an existing server closes just its own connection, and the server keeps running for the others. To delete a server explicitly from any client, call `sdk.destroyAcpServer(serverId)`. If the owner disposes first, its server is deleted; when another client uses the session again, the session is restored on a new server that this client then owns. A prompt sent after the server was deleted never reached the agent, so it is sent once more on the restored session and the call resolves normally. A prompt that was already running when the owner disposed may have reached the agent, so it throws `SessionRequestInterruptedError` instead (see [Session Restoration](/session-restoration)). If the owner exits without calling `dispose()`, the server keeps running until a client deletes it.
- **Permission requests.** A request belongs to the client whose prompt is running. If that client has no `onPermissionRequest` listener, it cancels the request, as a single client does. Other attached clients never answer on their own: without a listener they ignore it, and with a listener they receive it and may call `respondPermission`. Once any client has answered, the pending request is removed from the other clients, so a late `respondPermission` there throws instead of sending a second answer. If the prompting client dies while a request is open, no other client cancels it by default, and the turn waits for the server's agent request timeout (2 hours by default, see `--acp-request-timeout-ms` in the [CLI reference](/cli)). A supervising client can opt in with `cancelUnansweredPermissionsAfterMs` in `SandboxAgent.connect(...)`: it then cancels another client's request that is still unanswered after that many milliseconds, if it has no listener for the session.
- **History.** Each attached client receives every event, and events are stored once in the shared persistence driver (see [event ids](/session-persistence#event-ids-and-shared-drivers)). The events of a turn are stored by the client that sent the prompt, so the stored history (and the history replayed when a session is recreated) keeps the order prompt, then the agent's output. The other attached clients also keep the turn's events. After the turn ended they check the store: as long as the prompting client is still writing, they write nothing, and only when the turn is still incomplete and nothing changed in the store for 2 seconds do they store the missing events. A turn is therefore not lost when the prompting client dies mid-turn (the prompt's own result only reaches the client that sent it, so that one entry is missing then). Other clients deliver those events to their listeners with their own local `eventIndex`; use `event.id` to match them with stored history.

## Session configuration

Set model, mode, or thought level at creation or on an existing session:

```ts
const session = await sdk.createSession({
  agent: "codex",
  model: "gpt-5.3-codex",
});

await session.setModel("gpt-5.2-codex");
await session.setMode("auto");

const options = await session.getConfigOptions();
const modes = await session.getModes();
```

Handle permission requests from agents that ask before executing tools:

```ts
const claude = await sdk.createSession({
  agent: "claude",
  mode: "default",
});

claude.onPermissionRequest((request) => {
  void claude.respondPermission(request.id, "once");
});
```

See [Agent Sessions](/agent-sessions) for full details on config options and error handling.

## Events

Subscribe to live events:

```ts
const unsubscribe = session.onEvent((event) => {
  console.log(event.eventIndex, event.sender, event.payload);
});

await session.prompt([{ type: "text", text: "Give me a short summary." }]);
unsubscribe();
```

Fetch persisted events:

```ts
const page = await sdk.getEvents({
  sessionId: session.id,
  limit: 100,
});

console.log(page.items.length);
```

### Turn events

To know when the agent finished a turn or is waiting for a decision, without holding on to the `prompt(...)` call, subscribe to turn events. Every client attached to the session receives them, not only the one that sent the prompt, so an orchestrator can watch sessions that other clients drive:

```ts
import type { SessionTurnEvent } from "sandbox-agent";

const off = session.onTurnEvent((event: SessionTurnEvent) => {
  if (event.type === "turn_ended") {
    console.log(event.outcome, event.stopReason);
  }
});
// Same thing by session id: sdk.onTurnEvent(session.id, listener)
```

| `type` | When |
|--------|------|
| `turn_started` | A prompt was sent to the agent. |
| `turn_ended` | The turn is over. `outcome` is `completed`, `error`, `timeout`, `agent_exited`, or `cancelled`; `stopReason` is set when the agent reported one. |
| `awaiting_input` | The agent asked for a permission decision (`kind: "permission"`) and waits for the reply. |
| `input_resolved` | That request was answered, or the turn ended without an answer. |

A turn's `turn_ended` is delivered after the turn's other session events. Turn events are not stored in the session history (`getEvents`). See [Agent Sessions](/agent-sessions#track-turn-progress) for the outcomes in detail.

## Control-plane and HTTP helpers

```ts
const health = await sdk.getHealth();
const agents = await sdk.listAgents();
await sdk.installAgent("codex", { reinstall: true });

const entries = await sdk.listFsEntries({ path: "." });
const writeResult = await sdk.writeFsFile({ path: "./hello.txt" }, "hello");

// Directory as a streamed tar archive (ReadableStream<Uint8Array>).
const archive = await sdk.downloadFsBatch({ path: "./results" });
const archiveBytes = new Uint8Array(await new Response(archive).arrayBuffer());

console.log(health.status, agents.agents.length, entries.length, writeResult.path, archiveBytes.byteLength);
```

`downloadFsBatch(query, { signal })` resolves once the server has validated the request and returns the response body as a stream; path, symlink, and limit errors reject with `SandboxAgentError`. `uploadFsBatch(body, query)` is the matching upload. See [File System](/file-system#batch-download-tar) for limits.

## Desktop API

The SDK also wraps the desktop host/runtime HTTP API.

Install desktop dependencies first on Linux hosts:

```bash
sandbox-agent install desktop --yes
```

Then query status, surface remediation if needed, and start the runtime:

```ts
const status = await sdk.getDesktopStatus();

if (status.state === "install_required") {
  console.log(status.installCommand);
}

const started = await sdk.startDesktop({
  width: 1440,
  height: 900,
  dpi: 96,
});

const screenshot = await sdk.takeDesktopScreenshot();
const displayInfo = await sdk.getDesktopDisplayInfo();

await sdk.moveDesktopMouse({ x: 400, y: 300 });
await sdk.clickDesktop({ x: 400, y: 300, button: "left", clickCount: 1 });
await sdk.typeDesktopText({ text: "hello world", delayMs: 10 });
await sdk.pressDesktopKey({ key: "ctrl+l" });

await sdk.stopDesktop();
```

Screenshot helpers return `Uint8Array` PNG bytes. The SDK does not attempt to install OS packages remotely; callers should surface `missingDependencies` and `installCommand` from `getDesktopStatus()`.

## Error handling

```ts
import { SandboxAgentError } from "sandbox-agent";

try {
  await sdk.listAgents();
} catch (error) {
  if (error instanceof SandboxAgentError) {
    console.error(error.status, error.problem);
  }
}
```

## Inspector URL

When you call `SandboxAgent.start(...)`, prefer `sdk.inspectorUrl`. Some hosted providers return a browser-ready Inspector URL there.

```ts
import { buildInspectorUrl } from "sandbox-agent";

const url = buildInspectorUrl({
  baseUrl: "https://your-sandbox-agent.example.com",
  headers: { "X-Custom-Header": "value" },
});

console.log(url);
```

Parameters:

- `baseUrl` (required unless `fetch` is provided): Sandbox Agent server URL
- `token` (optional): Bearer token for authenticated servers
- `headers` (optional): Additional request headers
- `fetch` (optional): Custom fetch implementation used by SDK HTTP and session calls
- `skipHealthCheck` (optional): set `true` to skip the startup `/v1/health` wait
- `waitForHealth` (optional, defaults to enabled): waits for `/v1/health` before HTTP helpers and session setup proceed; pass `false` to disable or `{ timeoutMs }` to bound the wait
- `signal` (optional): aborts the startup `/v1/health` wait used by `connect()`
