---
title: "Session Restoration"
description: "How the TypeScript SDK restores sessions after connection/runtime loss."
---

Sandbox Agent automatically restores stale sessions when live session state is no longer available.

This is driven by the configured `SessionPersistDriver` (`inMemory`, IndexedDB, SQLite, Postgres, or custom).

## How Auto-Restore Works

When you call `session.prompt(...)` (or `resumeSession(...)`) and the saved session points to a stale connection, the SDK:

1. Reattaches to the agent server the session last ran on (`serverId`), for example after your client process restarted. Reattaching never starts a server. Only if the server rejects the client because that agent server does not exist does the SDK check the server's list of agent servers and, once the list confirms it is gone, start a new one.
2. Resumes the existing agent session when the agent supports it. The conversation continues as is and nothing is replayed.
3. Otherwise, creates a fresh session for the same local session id, rebinds the local session to the new runtime session id, and replays recent persisted events into the next prompt as context.
4. Applies the previously selected mode and config options (model, thought level, and others) again where the agent reports different values.

The same restore runs when a request fails because the agent server is gone (it was removed, for example because the client that started it called `dispose()`, or its agent process exited) or the agent no longer knows the session. When any request fails, the SDK asks the server whether the session's agent server still exists. The server stops listing an agent server as soon as its agent process exits, so a crashed agent is never reused.

- If the agent rejected the request because it does not know the session, the request is sent once more on the restored session.
- If the agent server was already gone when the request was sent, the server rejected it before any agent saw it, so the request is sent once more on the restored session. This is the usual case for a client that attached with `resumeSession` after the client owning the server disposed: its next prompt restores the session on a new server that it owns and resolves normally (see [Several clients on one session](/sdk-overview#several-clients-on-one-session)).
- If the agent server went away while the request was running (for example in the middle of a prompt turn), mode and config changes are sent again, but prompts and other requests are not, because the agent may already have run them. The SDK throws `SessionRequestInterruptedError` instead. Its `session` property holds the restored session, so you can send the prompt again if you want to.

Sessions on other agent servers are not affected. A session only moves to a new agent server once the server's list of agent servers confirms the old one is gone. Reattaching to a running agent server does not need that list, so `resumeSession(...)` works while the list cannot be read. If the server itself cannot be reached, or the old agent server is missing and the list cannot be read, nothing is restored: a failed request and `resumeSession(...)` throw the original error, and the saved session keeps its `serverId`, so a later attempt reattaches to the same agent server.

This happens automatically; you do not need to manually rebuild the session.

## Restoring settings

If a previous mode or config option cannot be applied again (for example, a model is no longer offered), the SDK still tries every other value, logs a warning, and throws `SessionConfigRestoreError`. Its `session` property holds the restored session and `failures` lists each value that was not applied. When this happens during `session.prompt(...)`, the prompt is not sent; the session is already restored, so sending it again works.

## Replay Limits

Replay payload size is capped by:

- `replayMaxEvents` (default `50`)
- `replayMaxChars` (default `12000`)

These controls limit prompt growth during restore while preserving recent context. They only apply when a session is recreated.
